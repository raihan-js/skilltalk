# Family Todo App — build playbook

> Generated by SkillTalk from a spoken interview with the project owner.
> **Agent: start with "Milestone 0" below. Do the setup yourself — don't hand it to the owner.**

## What we're building

I want a simple shared to-do app for my family. We keep forgetting chores and groceries, so everyone should see the list and tick things off from their phones.

- **For:** A small group — expected users at start: Under 100
- **Platform:** Website
- **Scale tier:** Starter — small user base — managed hosting and free tiers cover everything; keep it simple.
- **First working version wanted in:** About 2 weeks
- **Look & feel:** Bright and friendly, big buttons, something like Todoist but simpler

## How to work with me (the project owner)

My experience with tech: **Beginner**. Explain every technical word the first time you use it, with an everyday comparison. After each milestone add a short "What you learned" note (2–3 lines) linking to the playbook. Never assume I know where a setting or command is — give exact clicks or commands.

1. Before each step, say in 1–3 plain sentences what you'll do and why. After it, tell me exactly how to
   test it (what to run or click, what I should see).
2. One milestone at a time, on its own branch, finished with a pull request and green CI. Never push to main.
3. **Ask me before** anything that costs money (budget: $0/month), deletes data, adds a new
   service or library outside the stack below, or deploys to production outside the normal PR flow.
4. Secrets go in `.env` only. Tell me which key, where to get it, and where to paste it.
5. If a fix doesn't work the first time, switch to the bug-loop protocol (`/fix`). Never go in circles.
6. Keep `PROGRESS.md` up to date so any session can pick up where the last one stopped.

| Platform | **Website** | works in any browser, on phone and computer; fastest to build |

## Scale & reliability — build what this project needs, nothing more

- 🟢 **Environments — local, preview, production:** Local + PR previews + production. Use a separate dev database if the host allows it for free.
- 🟢 **Backups & recovery:** Confirm the database host's automatic backups are ON; export data before risky changes.
- 🟢 **Security basics:** Auth checks on the server, RLS on, input validation, dependency updates.
- 🟢 **Cost control:** Budget alerts on every paid service; the AI asks before adding anything paid.
- ⚪ **Speed — caching & CDN:** Your host already uses a CDN. Just keep images small and pages simple.
- ⚪ **Vertical scaling (a bigger machine):** Free tiers are enough at this size.
- ⚪ **Horizontal scaling (more machines) & load balancing:** Not needed. But write stateless code from day one (no files saved on the server).
- ⚪ **Background jobs & queues:** Do things directly and keep them fast. For scheduled tasks (like reminder emails) use the host's built-in cron, not a queue system.
- ⚪ **Containers (Docker):** Managed hosting runs your code without containers.
- ⚪ **Kubernetes:** Definitely not. Managed hosting does everything you need.

Full explanations (CI/CD, environments, backups, vertical vs. horizontal scaling, Kubernetes…) in
`references/engineering-playbook.md`.

## Guardrails (summary — full list in `references/guardrails.md`)

- Tests define done. Never delete, skip or weaken a test; never disable a hook or CI check.
- Small diffs, one concern per branch. Stay inside the stack; new tech → `architect` agent → owner's OK.
- No secrets in code or logs. No destructive commands without the owner's OK.
- **Privacy:** normal data; users only ever see their own or shared data they're allowed to see.
- **Owner's notes:** My mum isn't techy, so it has to be super obvious.
